1. ARCHITECTURE PRINCIPLES
1. Postgres is the source of truth. Business rules (status transitions, streaks, version numbers, timestamps) live in DB functions/triggers, so they cannot be bypassed from the client.
2. All writes that change workflow state go through RPC functions (start_task, submit_task, review_submission, ...). Clients never UPDATE status columns directly (RLS blocks it).
3. RLS enabled on every table. Default deny. Policies use SECURITY DEFINER helper functions (current_role(), is_admin(), mentor_owns_intern()).
4. Append-only history. Submissions, reviews, task events, and audit logs are never updated or deleted.
5. Server timestamps only (now() in the DB). Never trust client time.
6. Realtime via Supabase Realtime on notifications (filtered by recipient_id) plus invalidation of TanStack Query caches.
7. Do not expose raw UUIDs in UI. Show human-friendly codes (TSK-0042, ASG-0007) generated by sequences.

2.2 Auth & role system
• Use Supabase Auth (email + password). Public signup is disabled. Only Admin creates accounts via the admin-create-user Edge Function (service role), which also creates the profiles row and the role-specific row (interns or mentors).
• Roles are stored in public.profiles.role ('intern' | 'mentor' | 'admin'). Add a Custom Access Token Auth Hook that injects user_role and profile_status into the JWT, so RLS and the frontend can read the role without extra queries.
• Passwords are hashed by Supabase Auth (bcrypt). Never store or display plaintext passwords. Admin "reset password" sends a reset email or sets a one-time temporary password that the user must change on first login (must_change_password flag).
• Session expiry: JWT expiry 1 hour, refresh-token rotation on, inactivity timeout of 30 minutes enforced client-side (idle timer, then signOut() and redirect to /login?reason=expired). Deactivated users (status='inactive') are blocked by the auth hook and by RLS.
• Three login experiences: one /login page with a role selector (tabs: Intern / Mentor / Admin). After sign-in, verify the profile's role matches the selected tab; otherwise sign out and show "Wrong portal for this account."

2.7 Status transition matrix (enforced in a BEFORE UPDATE trigger and inside RPCs)
assigned           -> pending
pending            -> in_progress
in_progress        -> submitted
submitted          -> waiting_for_review
waiting_for_review -> approved | changes_requested
changes_requested  -> resubmitted
resubmitted        -> waiting_for_review
approved           -> (terminal; only admin override)
any                -> archived (admin/mentor owner)
Any other transition raises INVALID_STATUS_TRANSITION. Direct UPDATE of task_assignments.status by non-RPC callers must fail (revoke UPDATE privilege on that column from authenticated; RPCs run as definer).
2.8 Streak definition
An active day is a calendar day (in platform_settings.timezone, default Asia/Kolkata) on which the intern performs at least one meaningful action: starting a task, submitting/resubmitting a task, or submitting an assignment. Login alone does not count.
record_intern_activity(): upsert intern_daily_activity; if last_active_date = today do nothing more; if last_active_date = today - 1 then current_streak += 1; otherwise current_streak = 1; update longest_streak = greatest(...), total_active_days += 1, last_active_date = today. A nightly cron resets current_streak to 0 for interns whose last_active_date < today - 1.
